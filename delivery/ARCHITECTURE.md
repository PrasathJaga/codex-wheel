# Execution evidence architecture

The trusted controller authenticates reviewed source snapshots and approved
experiment/configuration inputs. The model gateway owns the API credential and
sends only the selected investigation context to Meta. A bounded proposal is
validated and frozen before execution; unsupported fields and unresolved references
remain rejected outcomes. The model cannot silently change the verifier or budget.

Baseline and candidate face the same selected intervention and relevant controls
in fresh worlds. Independent verification reads the committed ledger/order state,
checks action/event identities and retains the actual outcome. The report presents
recorded evidence; opening it runs no model, service or business experiment.

A repair proposal passes allowed-edit checks, unchanged tests and the original
experiment/control verification. The demonstration's repair tasks supply healthy
source for bounded restoration. Verification supports the tested conditions, not
universal correctness or general self-healing.

## Components and evidence

| Component | Role | Inspect |
| --- | --- | --- |
| Source-aware investigator | Connects relevant source behavior and chooses constrained inputs/intervention | Refund proposal and inventory plan/source references in the report |
| Frozen experiment | Binds input, source identities, intervention and trial conditions | Original archive lock/proposal records |
| Executor | Runs baseline/candidate and captures actual tool responses and persisted effects | World state, event/action traces, runtime identities |
| Independent verifier | Determines effect/lifecycle outcomes; model prose cannot override it | Three paired trials and controls before/after restoration |
| Bounded repair | Proposes allowed restoration and verifies it | Original repair proposal, unchanged test records and repaired worlds |
| GitHub/reviewer surface | Links the finding to a reviewed change and its evidence | Fixture PR27 result, original Actions and downloadable static report |

## Runtime boundaries

The demonstrated refund/inventory archives retain their actual historical
boundaries: Java services use restricted containers; the unchanged Python peer is
trusted-host execution. Do not describe those older runs as full OS isolation of
every component. Later generic Java/Python controls use the shared restricted
container lifecycle, with scoped capabilities documented separately.

External project containers receive neither the Wheel checkout nor Meta/GitHub
credentials. No real payment system or customer records are involved. Artifact
hashes establish recorded input/evidence identity; references resolving does not
independently establish the correctness of every causal explanation.

## Product direction

The future platform aims at broader pre-production investigation, environment
reproduction, test selection and verified repair. The current submission establishes
supported executable evidence loops. General framework onboarding, independently
prepared evaluation, production effectiveness and external adoption remain open.
