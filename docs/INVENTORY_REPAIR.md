# Inventory bounded restoration v1

This phase closes the inventory loop within a declared supplied-answer repair boundary. It does not broaden intake, prove additional coverage beyond JUnit, repair an unfamiliar defect or automatically merge any code. Fixture PR #34 remains deliberately defective and must never merge.

## Evidence and sequence

1. Authenticate the exact original investigation ZIP using its registered digest. Retain the unchanged ZIP and extracted parent evidence in the output. Check pinned source/revision identities, Meta proposal citations/plan hash, paired identities, action traces, state files and independent parent verdicts.
2. Admit the same healthy baseline and known candidate with all other source/tests/oracle bytes unchanged. Run fresh Java tests for both and preserve the candidate's actual failure result. Package the candidate only for observation.
3. Execute 12 fresh broken-stage worlds: three baseline/candidate pairs for the original happy-path control and three for the original Meta-selected sequence. A valid baseline, passing control and reproduced candidate lifecycle failure are required before inference.
4. Request one new Muse Spark 1.3 repair proposal. Provide healthy/candidate source, the original frozen experiment and three fresh failing candidate records. Return one unique old_text/new_text replacement. The entire resulting file must equal supplied healthy baseline bytes.
5. Freeze the admitted proposal and restored source, run unchanged Java tests/package, then execute 12 fresh repaired-stage worlds using the exact same selected/control actions. Candidate becomes the tested repaired JAR; baseline and fresh runtime images remain unchanged within this repair run.
6. Retain all original/fresh failure and repair evidence, rejection/error records, model receipt and usage. No fallback patch or retry is allowed.

## Caps and authority

The prospective policy is `evaluation/inventory_repair_v1.json`: one new request, 6000 completion-token ceiling, zero automatic retries and at most 24 fresh worlds. Twelve historical parent worlds are kept separately and are never counted as fresh. Any invalid baseline, missing access, archive/source integrity error, rejected proposal or failed repair verification stops the attempt.

The only possible admitted change restores the removed ACTIVE-state rejection in `InventoryStore.confirm`. Ownership, persistence, validation, tests, evaluator, Python peer and verifier remain unchanged. Application source is repaired in temporary build space and preserved as an artifact; no application branch is patched or merged automatically. Healthy-source equality deliberately limits generality.

The Java producer uses the existing constrained Docker runtime. The unchanged Python peer and independent verifier stay in the trusted host harness, as in the prior inventory investigation. Explicit expiry events model lifecycle ordering; there is no physical-clock or distributed in-flight race claim. A repaired finite set of experiments is not universal correctness.

## Run and outputs

Ordinary PR CI runs unit tests only. A dedicated named push branch is reserved for the single paid attempt; the workflow downloads the exact parent ZIP with read-only GitHub access and supplies the model key only to the runner step. Credentials are removed before subprocesses and are not persisted in evidence.

Outputs include `origin-investigation.zip`, `parent/`, `repair-lock.json`, source snapshots, baseline/candidate test logs, `broken-*-worlds.json`, `repair-request.json`, `repair-proposal.json`, `repair-admission.json`, `restored-InventoryStore.java`, `repair-tests.*`, `repaired-*-worlds.json`, per-world traces/state, runtime/probe/integrity records, summary and an escaped static HTML index. Binary runtime closure is not exported; image/JAR identities identify the observed executions.

If successful, the precise claim is: a fresh Meta proposal restored the supplied healthy baseline, unchanged tests passed and the same original failure sequence plus control passed in repeated fresh execution. Existing JUnit had already caught the candidate; that result remains visible.
